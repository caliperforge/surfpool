# Review rules for solana-foundation/surfpool, from its own Greptile reviews

## Other findings

- The wait finishes too early (P2, 1×): `getSlot` above the response's `context.slot` does not mean every override has landed. If the current slot is 123 and the caller supplies base slot 200, slot 124 passes this check before any override runs. A nonzero `scenarioRelativeSlot` has the same problem, so callers following this advice can read unchanged accounts.
- Clock thread outlives the test (P2, 1×): The new test leaves a clock thread running after it finishes. `start_clock_runloop` never exits when either channel disconnects, so dropping the test's channels leaves it waking roughly 1,000 times per second for the rest of the test process. Add a shutdown path and stop the thread during cleanup, including when the assertion fails.
- Last valid pair lacks coverage (P2, 1×): The boundary test checks ID `0` and overflowing IDs, but never checks the last valid ID, `5`. Add `assert_eq!(surfnet_port_pair(5), Some((58_899, 58_890)))` so a future change that stops scanning one pair too early cannot pass this test.
- Default SOL funding fails (P1, 1×): Omitting `token_amount` now makes SOL funding fail. `run` defaults to `100_000_000_000` and scales it by `10^9`, which exceeds `u64::MAX`. The new check therefore rejects the default request before sending it.
- New overflow test fails (P1, 1×): These inputs calculate `433_000 + (u64::MAX - 1_000_000_000)`, which fits in `u64`. The helper returns success, so the assertion expecting `ArithmeticOverflow` fails. Set `current_updated_at` to `0`, for example, so the test actually reaches the new error path.
- Explicit time jumps get rejected (P1, 1×): The new `checked_mul` rejects `AbsoluteSlotAt` requests when the unused calculated timestamp overflows. `calculate_time_travel_clock` calls this helper before replacing that time with the supplied timestamp.
- Flame graph counts units twice (P1, 1×): If logs end after a CPI finishes but before its caller's `consumed` line, `folded()` emits the CPI's units while `unattributed()` includes them again in the remainder. A 1,000-CU transaction with a completed 200-CU CPI under an unfinished caller therefore produces a 1,200-CU flame graph.
- Program names can rewrite output (P2, 1×): IDL names reach the terminal without escaping. An RPC response can put terminal controls in `metadata.name`; `label()` returns them unchanged, and `render()` prints them. A crafted name can clear or rewrite the displayed profile.
- Cleanup drops recorded slots (P1, 1×): On persistent networks, `confirm_current_block` calls `garbage_collect` before this read. That rebuilds LiteSVM and restores five sysvars, but not `SlotHistory`. This code then adds the current slot to the fresh history and streams it, losing records of earlier blocks produced during the same run.
- Finalized reads return old balances (P1, 1×): `account_at` can return an old fetched value after `answerable` moves the response to a newer slot. For example, an Alpenglow finalized read captures slot W−1 and fetches an account before a transaction changes it in W. If W closes before encoding, `answerable` raises the response slot to W and block close removes the saved version at W. `None => fetched` then returns the pre-transaction value labeled W, although the transaction is finalized there.
- Remote holders show different amounts (P1, 1×): The slot-based token amount fix skips holders returned only by the datasource. `get_token_largest_accounts_local_then_remote` keeps their already-computed amounts unchanged; the owner, delegate, and program scans do the same. After local time travel crosses a scaled-amount multiplier's start time, a cached holder uses `clock_at(read.slot())`, while an uncached holder of the same mint keeps the datasource's amount.
- Remote amounts use newer time (P1, 1×): `merge_remote` keeps the slot chosen before the remote request, but reads the mint and `Clock` again afterward. If blocks finalize during the wait, `confirm_current_block` can delete the saved values needed for that slot. Remote holders then use newer mint settings or time, while local holders keep amounts calculated at the reported slot.
- Balance uses the wrong mint (P1, 1×): `get_token_account_balance` selects the mint at its first read slot, then reads the token account again at a fresh slot after fetching that mint. If the account is closed and recreated with another mint during the wait, the second read combines the new account's amount with the old mint's decimals and rate settings. A concurrent `setAccount` rewrite can do the same, producing the wrong token amount.
- PDA inputs block account writes (P2, 1×): `account_data_values` misses inputs used only by a keep-alive PDA. When a raw-layout template's main address is a pubkey, an `Input` used by a keep-alive `property_ref` seed remains in the fields to write. `keep_alive_inputs()` only covers `KeepAliveAddress::Input`.
- Recurring writes lack test coverage (P2, 1×): The new tests cover parsing, address resolution, and registry lookups, but none runs a non-empty keep-alive binding through `SurfnetSvm`. The bundled registry has no keep-alive imports, so existing scenario tests only reach the empty path.
- Offline accounts get downloaded (P1, 1×): When a keep-alive import targets an account that is missing locally but marked offline, `keep_alive_overrides` now enables `fetch_before_use` just because a remote client exists. The fetch path does not check `offline_accounts`, so it downloads and restores an account the user explicitly excluded from remote downloads.
- Failed overrides start keep-alive (P1, 1×): `apply_overrides` adds a `KeepAliveSource` before checking the account or writing its fields. If a raw-layout write fails, the loop logs the error and continues, then returns that source for enrollment. An invalid price override can therefore start refreshing a separate oracle every slot even though the price change never happened. Enroll each source only after its override succeeds.
- PDA seeds suppress field writes (P1, 1×): The new code adds every keep-alive PDA seed reference to `pda_refs`, so `account_data_values` drops matching values even when they are writable fields. An override that writes an oracle pubkey and uses that pubkey to derive a keep-alive account will leave the oracle field unchanged. Filter input-only properties without dropping writable fields used to derive a different account.
- Saved programs lose required data (P1, 1×): The strict database branch calls `map_account()`, which drops the saved program’s coupled `ProgramData`. On restart, a `null` entry can fetch a non-executable upstream account at an address where the database holds a locally deployed upgradeable program. That fetch queues no program data. This branch then restores the saved program without its saved `ProgramData`, so strict startup fails despite a complete saved pair.
- Misspelled locks do nothing (P2, 1×): `lock_cheatcode_methods` accepts unknown names and starts successfully. For example, `surfnet_setaccount` leaves `surfnet_setAccount` available without warning. The CLI and runtime lock calls reject unknown names, but this startup path silently accepts them.
- Restored balances prevent startup (P1, 1×): A snapshot containing the configured payer or an `airdrop_addresses` entry can make `start()` fail. The runloop applies startup airdrops first, then replaces those balances with snapshot values. But the SDK still waits for every balance to equal `airdrop_lamports`, so a valid restored balance with a different amount causes a startup timeout.
- Unused ticks count as late slots (P2, 1×): `coalesced_slots` counts dropped ticks in every block mode, but the SDK describes it as a count of late slots in `BlockProductionMode::Clock`. In `Transaction` or `Manual` mode, a slow transaction or remote fetch can fill the tick queue and raise this count even though ticks do not produce blocks. Callers can then mistake unused ticks for degraded slot timing and reject an otherwise valid run.
- Simulated profiles ignore the limit (P2, 1×): `max_profiles` promises to limit executed and simulated profiles separately, but only executed profiles use the limit. `simulated_transaction_profiles` uses an unbounded map, and each `profile_transaction` call adds a new entry. SDK users could rely on this setting to bound memory while simulated profiles keep growing. Document that this setting limits only executed profiles, or apply it to simulated profiles too.
- Profile tags stop working (P1, 1×): With in-memory storage, the new `FifoMap` drops old simulated profiles but leaves their IDs in `profile_tag_map`. Once a tagged profile is dropped, `get_profile_results_by_tag` fails for the whole tag, even when newer profiles remain.
- Empty batches get no reply (P2, 1×): Sending `[]` over WebSocket now gets no reply. `dispatch_batch` treats an originally empty batch like a batch containing only blocked notifications and returns `None`. JSON-RPC requires an Invalid Request reply for an empty array, so clients waiting for that reply will time out. Reject an originally empty batch before filtering blocked calls.
- Clock reads keep older slots (P1, 1×): `ReadSlot::covering` still misses writes to the `Clock` account. Every `confirm_current_block` advances the slot and writes the new clock through `self.inner.set_sysvar`, which bypasses `account_update_slots`. A confirmed or finalized `getAccountInfo` for the clock therefore returns data whose `Clock.slot` exceeds `context.slot`. Clients comparing those slots still hit the inconsistency this PR fixes. Track these writes too, and add a clock-account regression test.
- Small reads walk all accounts (P2, 1×): `covering_every_account` walks the entire `account_update_slots` map on every scan request. For example, `getSupply` reads stored totals but now also visits every tracked account under a read lock. Its cost grows with unrelated account writes, and writers must wait for the walk to finish. Keep a latest-write slot alongside the per-account map so scans can read it directly.
- Parsed reads miss mint writes (P1, 1×): `getAccountInfo` covers only the requested account, but a `jsonParsed` token response also reads its mint to compute `uiAmount`. If the holder's write has aged past the requested commitment and only the mint is updated, the response uses the new mint settings under an older `context.slot`. `getMultipleAccounts` has the same gap when the mint is not requested.
- Reset balances keep old slots (P1, 1×): `surfnet_resetAccount` reaches `purge_account_from_cache`, which replaces the account with `Account::default()` without recording that write. If the account's previous write has aged past the requested commitment, a subsequent `getBalance` returns zero while this lookup keeps a slot from before the reset. Clients comparing update slots still hit the inconsistency this PR aims to fix.
- Restarts lose scan coverage (P1, 1×): Accounts and their owner indexes survive a restart with persistent storage, but startup initializes `account_update_slots` empty and `latest_account_write_slot` to zero. After a transaction writes an account at slot N and the server restarts at N+1, a finalized `getProgramAccounts` can therefore return that account under a slot before N.
- Cancelled filters keep doing work (P2, 1×): Unsubscribing from `mentionsAccountOrProgram` leaves its entry in `block_subscriptions` until a matching transaction appears. The WebSocket task drops its receiver, but this early return skips `tx.send()`, which is the only check that removes the entry. Repeated subscriptions to unused accounts therefore grow the list and keep checking transactions after users unsubscribe. Remove cancelled entries independently of whether a block matches.
- Skipped slots inflate confirmations (P1, 1×): After a forward time travel with Alpenglow disabled, `found_transaction` now keeps earlier transactions confirmed until enough real blocks follow them. But `confirmations` still subtracts absolute slot numbers. A jump of 1,000 slots can therefore report more than 1,000 confirmations when only a few blocks follow the transaction. Clients waiting for a confirmation count can finish too early.
